# Render Graph Progress

Working log for [RenderGraphDesign.md](RenderGraphDesign.md). Records the plan per phase, what landed, findings and learnings. The design doc stays the source of truth for intent; deviations are recorded here with the reason.

## Decisions

* Vulkan 1.3 core is the minimum (dynamic rendering + synchronization2 required). `VK_KHR_dynamic_rendering_local_read` is enabled with its first user, pixel-local reads (3.4); `VK_KHR_unified_image_layouts` stays disabled, with no RHI query, until the `GENERAL` collapse has a user.
* Metal is changed alongside Vulkan in each step; Metal correctness is gated by the macOS CI jobs (no local Metal build).
* Phase 0 is implemented in full.
* Deviations carried into Phase 1: `RHIAttachmentSignature` has no per-slot write mask (§7.1), and no store op lowers to `STORE_OP_NONE` (§6.5; the store op the design calls `None` is `RHIStoreOp::DontCare`); both belong with load/store inference and pass merging in Phase 1.

Deviations from the design, from reading Phase 0 code:

* Imports and transients are seeded from the physical image's tracked `{layout, access}` and the graph writes state through to the tracker per pass (design §4.1, §6.4, §6.6 updated). A transient seeded from `Undefined` with no source access would race the previous frame's use of the pooled image, and the swapchain's first write must chain to the acquire wait as `VulkanRenderPass::Begin` does today.
* The graph reuses Phase 0's `RHIAccess`/`RHIShaderStageMask`/`RHIImageLayout` inside accesses; the builder methods are the §4.2 vocabulary.
* `Present` needs no access: `EndFrame` transitions the back buffer from tracked state.
* `RHIImageLayout` has no read-only depth layout; `DepthTest` uses the depth attachment layout until a pass samples and tests the same depth.
* Graph validation and the pass contract (each declared image left in its declared state, checked after every pass) abort in every build, because `ASSERT` compiles out of the Release builds CI runs.
* Shader variants have no Phase 1 user; they arrive with pixel-local reads in Phase 3.
* The two Phase 0 deviations (per-slot write mask, no store op lowering to `STORE_OP_NONE`) have no user without merging and move to Phase 3.

Phase 1 findings:

* `BeginRendering` takes the opening barrier batch (and `EndRendering` a closing one) instead of recording none: the pass's timer and debug label must cover its attachment barriers, and the Metal encoder needs the name and timer at creation. The graph passes each pass's batch the same way. `EndRendering`'s batch only serves the legacy final layouts and can go with `RHIRenderPass`.
* Final layouts live on `RHIRenderPass::Attribute`, not in `RHIRenderingInfo`, which is pure lowering input. `VulkanRenderPass`/`MetalRenderPass` are gone: `BeginVulkanRendering` and `CreateMetalRenderPassDescriptor` lower an info; Metal builds a fresh descriptor per pass, so a timed pass's sample buffer never leaks into a later untimed one.
* Tracked state still differs between backends where only backend code transitions images: Vulkan `Upload`/`UploadFaces` (TransferDst → Read), `EndFrame` (→ Present) and NRD user images. Shared golden graph shapes that seed from those images need these transitions in common code first (TODO entry).
* Compute passes still use `RHIPass::BeginTimer`/`active_timer_`; the render path selects the timer (`SelectTimer`) and the context begins it.
* `ScreenQuadPass` keeps five virtual hooks nothing overrides since `BlurPass` is gone; `SkyBoxPass`'s non-skymap branch looks unreachable from both raster renderers. Both are candidates to delete rather than port in 1.8/1.9.

* Always-on checks: `ASSERT` compiles out of Release, so graph validation and the pass contract use `RGCheck` (`Log(Error)` + `DumpAndAbort()`).
* The transient pool keys on (format, extent) with usage as a superset match; images carry no sampler (review A1). `RGTexturePool` is owned by `RenderFramework` and outlives renderer recreation (as `RHIRenderTargetPool` did, which `pipeline_switch_pool` checks), serves one graph at a time (Compile → graph destruction) and releases images unused for `UnusedGraphsBeforeRelease` graphs.
* `DepthTest` synchronizes as a depth write while its store op is `DontCare` (which writes depth); both change together when a distinct `RHIStoreOp::None` lowers to `STORE_OP_NONE`, which Phase 3 did not need (TODO entry).
* One test case needs two registry entries when it must run under `validate_sync` (Vulkan only) and on Metal (`render_graph_compile`, `render_graph_sync_validation`).
* Graph raster passes are untimed until Phase 2 (`RHIPass::SelectTimer` is private to the render-pass path); compute passes record their barrier batch inside `BeginComputePass`, so the pass timer covers it.
* The External contract is strict (declared layout, accesses within the declared ones). Legacy passes wrapped in 1.3–1.6 therefore end in their attachment layouts (final layout = attachment layout) and the graph derives the transition to the next reader.

* Golden graph shapes: `RenderFramework::RequestGraphDump(name)` asks the renderer for its next graph's dump, written to `screenshots/<name>.json` (pulled from devices like screenshots); the `render_graph_dump` test case requests one and `tests/render_graph/graph_shape_test.py --golden <pipeline>` diffs a line projection against `tests/render_graph/golden/<pipeline>.txt` (`--update` rewrites it). Goldens run headless: a windowed Vulkan back buffer waits on `Present`, which Metal does not track.
* Wrapping legacy passes needs no final-layout changes: `RHIRenderPass::Attribute` final layouts default to the attachment layouts (only `ClearTexturePass` overrides them). The legacy `BeginRenderPass` inside an External pass records a redundant discard barrier after the graph's; it disappears with native passes.
* The back buffer imports as `GetBackBufferRenderTarget()->GetColorImage(0)`, single-sampled on both backends; Vulkan re-points it on acquire, before `Render`.
* `AddReadback` creates its staging buffer inside the execute lambda (a transient's size is known only after compile), against D3's rule that execute touches only captured state; resolve with a setup-time texture query or `RGBuffer` imports (1.10).
* `cpu_render_static_64spp` (64 spp, FLIP gate 0.1) measured 0.0865 on ubuntu-glfw lavapipe; the CPU tracer reseeds per pixel and sample, so the value is deterministic per platform. The converged local `cpu_render_static` keeps its meaning.
* The CI toolchain enables `-Wshadow-uncaptured-local`: lambda init-captures must not reuse an enclosing local's name.

* Denoisers are one External pass each (`Denoiser::AddTo(graph, DenoiserInputs)` returns the displayed texture), not the Compute pass of design §8: NRD's pack, ReBLUR and resolve open their own compute passes, and MetalFX encodes on the raw command buffer. Internal images (NRD pool, `IN_*`/`OUT_*`, MetalFX prepared textures) keep their own transitions; declared images are left to the graph. `DenoiserDesc::accumulator_format` lets NRD create its output and history at construction.
* The MetalFX scaler output carries shader-write usage so display frames can declare the scaler's write (usage check on imports); an `RGBuilder` access for foreign writes would avoid it (TODO entry).
* The GPU golden needs a frame that still traces: `render_graph_dump_accumulating` dumps once the scene is fully loaded, and again until the dumped frame has a live `PathTrace` and neither `ClearAccumulator` nor `BuildTLAS` (the frames around the end of loading can have either), while `render_graph_dump` (screenshot-ready) would catch a converged frame that records no trace. `gpu_graph_shape` runs on ubuntu-glfw only (macOS CI has no ray tracing, so the pipeline falls back to forward).
* lavapipe runs the GPU path tracer fast enough for `gpu_render_static_64spp` (1280×720, 64 spp, FLIP gate 0.1, measured 0.0858) on ubuntu-glfw; NRD and MetalFX run in no CI job.
* `ToneMappingPass::SetInput` recreates its uniform buffer, so the exposure uploaded in `Update` is lost on the frame the input switches (pre-existing).

* `RenderGraph::Import` returns the first import's texture when an image is imported again, so passes sampling one image (IBL maps, sky map overrides, debug outputs) need no coordination. Forward's and Deferred's graphs do not depend on `render_scale` (tone mapping upsamples in its own pass); image sizes of imports are not in the dump.
* Forward and Deferred share `Renderer` helpers for the shadow, IBL imports, sky box and tone mapping/debug output wrappers; they move onto the pass classes (`AddTo`) with the native conversions (1.8/1.9). The clears declared on these External passes mirror what the legacy passes clear to.
* Sampled-only imports of uploaded images agree across backends in steady frames (Vulkan's upload leaves `Sampled(All)`, Metal converges after the first graph frame), so the forward and deferred goldens run on macos-macos and ubuntu-glfw.
* Passes declare the IBL maps the renderer's `ibl_` has ready, not what `ForwardMeshPass`/`DirectionalLightingPass` bound: while a new IBL cooks, the passes keep the previous maps bound and undeclared (never written, so no hazard). Native passes (1.9) bind what they declare.
* Pre-existing defects found in the port (not fixed): `DirectionalLightingPass::SetIBL(nullptr)` dereferences its argument (§15 defect 8) and `BindPixelShaderResources` uses `ibl->GetBRDFMap()` unchecked; Deferred's `UpdateOutputMode(SceneColor)` never resets the sky box override, so leaving the IBL map debug modes keeps showing the IBL map.

* Vulkan TLAS updates (`VulkanTLAS::Update`, MODE_UPDATE) require the TLAS built with `ALLOW_UPDATE`; it was built with `PREFER_FAST_TRACE` only, which core validation reports only when async scene loading changes a primitive after the first build (timing-dependent). The TLAS is built for updates now, with scratch sized for both; Metal already built for refits.
* Shader bindings dirty their descriptor set by resource id (`GetId()`), not address, so pooled images recreated at a freed address never keep a stale set.
* Removing `ToneMappingPass::SetInput` also removed its uniform-buffer recreation, so switching the displayed image no longer loses that frame's exposure.
* `MetalUiHandler::Init` needs no early `ImGui_ImplMetal_NewFrame`: the 1.92 backend sets `RendererHasTextures` at init and creates its device objects in the first `NewFrame`, which the `Ui` pass calls before drawing.
* A sampled access binds the sampler its pass supplies (review A1). Each screen pass chooses its input filter (`ScreenQuadPass::InputFilter`): tone mapping, `Upsample` and `GraphView` filter bilinearly with edge clamping when they resample a format the device filters linearly (`RHIContext::SupportsLinearFiltering`), otherwise nearest; `Present` samples nearest when the back buffer is an integer multiple of Screen in both axes (1:1 included, compared along the pre-rotated axes) and filters like them otherwise. The device query generalizes main's `ToneMappingPass::GetInputSampler` exception for `RGBAFloat`. Differences from main: on a device that filters `RGBAFloat` linearly, the GPU renderer's tone mapping at `render_scale` < 1 filters the accumulator and NRD output bilinearly (main: nearest); `Present` filters bilinearly where the back buffer is not an integer multiple of Screen (main: nearest, except the CPU renderer), and the CPU renderer's `Present` samples nearest (main: bilinear) at integer multiples above 1:1 (HiDPI). MetalFX outputs at output resolution, so tone mapping samples it nearest, as before.
* Renderers follow the template method of design §5 (review R6, R12). `Renderer::Render()` is not virtual: it creates the graph, calls the renderer's `BuildGraph(graph)`, which returns the scene texture, adds the post chain and executes the graph. The post chain is a `PostChain` the renderer owns (`Renderer::InitPostChain`), holding the screen pass (`ToneMapping`, `Upsample` or none), `Ui`, `Present`, `GraphView`, the graph-view state and the pending screenshot; `Renderer` keeps the pass timers and the dump requests. Forward and Deferred derive from `RasterRenderer`, which holds the shadow pass, the sky box, the IBL cook bookkeeping and the sky proxy tracking, and adds the IBL cook, the shadow map, `LightingInputs` and the sky box around the scene passes each adds (`AddScenePasses`). Graphs, dumps and images match the per-renderer structure it replaced; only the order of independent passes differs in two places: Deferred creates `GBuffer` after the post chain, and Forward uploads the shadow pass's frame data before the base pass's.
* `RenderFramework` owns the graph texture pool, so a pipeline switch reuses the images both pipelines' graphs hold (at least the post chain's Screen); `pipeline_switch_pool` requires every new renderer to reuse one.
* `RGBuilder::SampledOrPlaceholder` binds an image outside the graph where an input is missing (no directional light, IBL map not ready), so no pipeline keeps a pooled image an earlier graph bound. Importing the RHI dummy textures instead would declare one image twice (shadow and BRDF share one, diffuse and specular another).
* A pass that draws or dispatches nothing skips the binding check (`RHICommandContext::GetPipelines` is empty): an empty or loading scene draws no mesh.
* `PipelinePass::Render` is gone with the last legacy render-target pass; `ClearTexturePass` and the IBL cook passes keep a plain `Render` until 1.10.
* The output mode is a function of the config each frame (`GetSkyBoxMap` in `RasterRenderer`), which fixes Deferred's sticky sky override and removes `SetIBL` (defect 8) and the unchecked BRDF bind. An IBL mode whose map is not ready shows the scene; the BRDF mode culls the scene passes.
* Deferred lighting samples scene depth edge-clamped and nearest, at texel centres at the same resolution.
* Buffers and acceleration structures are imports (`RGBuffer`, `RGAccelerationStructure`) synchronized by memory barriers planned with the access rule (`TransitionAccess`, which the image rule applies within one layout), seeded from and written through to an `RHITrackedAccess` that `RHIBuffer` and `RHITLAS` hold as a member. The CI clang-tidy rejects it as a second base (`misc-multiple-inheritance`); the local clang-tidy 18 does not report that check.
* `RHITLAS::Build`/`Update` only stage a change (dirty BLAS builds, instance writes, allocation); `RecordBuild` records the staged build or refit in the GPU renderer's `BuildTLAS` Copy pass, and `PathTrace` declares and binds the TLAS read. A rebuilt TLAS takes a new resource id, so bindings follow it. BLAS builds and Metal compaction stay before the frame's passes.
* The readback's staging buffer is created when the pass is added (`RenderGraph::GetFormat`/`GetSize`) and imported, which resolves the execute-time creation noted above.
* Texture accesses may cover a mip or a single subresource (`RGTexture::Mip`, `Subresource`); planning keeps a state per subresource and emits one barrier per uniform run of mips within a layer. Store inference looks for the next overlapping access.
* The IBL cook records as graph passes: Forward and Deferred start their graphs with `ImageBasedLighting::AddCookPasses`, `IblCookAccelerator` runs one step per frame in a graph of its own. The first step clears each subresource of the cooking map in its own Raster pass (30 for specular); folding the clear into the first dispatch would change the cooked output. Cook dispatches are now ordered against each other across frames.
* Only the Forward and Deferred graphs cook the IBL; `SkyRenderProxy::Update` no longer cooks it in every pipeline. The GPU and CPU pipelines never sample the IBL, so under them no map cooks and none is persisted through the artifact callback; the first Forward or Deferred frame cooks it.
* The back buffer is an image (`RHIContext::GetBackBuffer`): Vulkan's headless image or the swap chain image acquired for the frame, Metal's back buffer color. RHI tests render through `BeginRendering` over an `RHIRenderingInfo` with barriers from `RHIImage::TrackTransition`; `render_target_pool` went with the pool.
* `RHIColorAttachment::resolve_image` is gone until MSAA returns through `ResolveTo` (D20). The GPU renderer's accumulator is a plain image, so it no longer survives renderer recreation; the first frame clears it.
* `RHIImage::Transition` stays: NRD, MetalFX, IBL `Finalize`, uploads, readback and `EndFrame`'s present transition still use it. It takes the command context to record into.
* `BeginRendering` takes the `RHIPass` that times it (`RHIContext::CreateRenderPass(name, need_timestamp)`), the shape for Phase 2's per-pass timing of graph raster passes.
* A headless Metal back buffer owns a texture; a windowed one takes each frame's drawable. A render pass with no valid attachment fails its command buffer, after which Metal ignores the process's later command buffers, so every readback (screenshots, buffer tests) returns stale data rather than failing at the faulty pass. A CI bisect by temporary revert is the fastest way to locate such a pass.

Phase 2 findings:

* Graph raster timers live in `Renderer` (`RGPassTimers`, one timed `RHIPass` per pass name), so a pipeline switch or resize reports no times for its first `max_frames_in_flight` frames; `IblCookAccelerator` and the synthetic tests execute without timers. The dump moved after `Execute` because a slot's time is read at the pass's first begin in the frame; a Metal timer can resolve to -1 (no valid sample), so the dump filters on `gpu_ms >= 0`, not on status.
* Every raster pass name now holds one `MTLCounterSampleBuffer` per frame in flight (about 30 per renderer on Metal). Whether a physical Apple GPU limits the number of sample buffers is unverified (macos-macos reports timestamps unsupported); a failed creation is an `ASSERT` only. Part of the open physical-GPU run.
* A test that pools across frames must destroy each graph before its pool.
* Declaration validation reads each pipeline's tables when the pass ends (a resource rebound between draws of one pass is not seen; no pass does that) and checks no shader stages. Placeholders and RHI dummies are never imported, so they pass without weakening the check. Aborting checks throw under test (`RGErrorsThrow`), and `render_graph_errors` makes one mistake per check; the Raster pass that records raw commands without `NativeAccess` is left out, because it throws inside the rendering the graph began.
* The IBL diffuse and specular cooks sampled the environment map, which the scene passes import as the sky map, without declaring it; they declare it `Sampled` now. The GPU cook runs in no CI job, so `ibl_parity` needs a local run on a GPU.
* A graph view needs a single-layer texture a float `Texture2D` can sample and that has contents when the post chain is added: the integer GBufferPacked, depth-stencil formats, cube maps and the IBL cook maps (no texture usage) fall back to the frame, so a UI choice never reaches an `RGCheck`. Screen and BackBuffer are created by the post chain itself and cannot be viewed. `deferred_graph_view_shape` views SceneDepth (golden `deferred_view.txt`), `deferred_graph_view_fallback` names GBufferPacked against the deferred golden. The view pass is `GraphView`; `output_image` now only picks the sky-box map.
* `GraphView` filters bilinearly only a format the device filters linearly, so viewing an `RGBAFloat`, `R32Float` or `D32` texture at `render_scale` < 1 is never a validation error.
* The viewer's pages go to `screenshots/captures/render_graph_<case>.html`: every graph case runs with `--clear_screenshots`, which deletes only top-level files, and the Android pull keeps `captures/`, so CI uploads each case's page with the test screenshots. The iOS runner replaces the whole screenshots folder per copy (no graph case runs there). The dump names each resource's type and dumps its lifetime as pass indices, so the grid needs no resource order and maps lifetimes to repeated pass names correctly; physical-pass bands and memoryless badges wait for the Phase 3 dump fields.
* The graph page asks the renderer for each next graph's dump through a callback (`Renderer::RequestGraphDump(on_dump)`) only while it is drawn, and `RenderFramework` publishes it under a mutex rather than through a main-thread task, which could outlive `RenderFramework` at shutdown. Whether a view is active is read from the dump (the `GraphView` pass's first access). Only texture rows are selectable (the dump's resource `type`), and lifetimes name passes by index into the dump's passes. The page has no automated test (ImGui is not created headless).
* The screenshot and graph-dump names read `render_config_.pipeline` on the main thread while `NewFrame` copies the config (pre-existing race; TODO entry).
* `render_graph_pass_timing` on ubuntu-glfw lavapipe measured 0.087 ms (Compute) and 0.133 ms (Raster).

## Phase 3: on-chip

Owner decisions:

* Slang 2026.19 in its own step. The pinned 2026.12.2 already lowers `SubpassInput` to `[[color(n)]]` (a stale local `build_cache` at 2026.1.1, which rejects it with error 36107, suggested otherwise); the step fixes the reinstall check that let caches keep any slangc, and bumps to the newest release, whose code is identical.

* Slang (2026.19, and 2025.7.1/2026.8 from the Vulkan SDKs) ignores the `SV_Target` index of a returned value: Metal emits `[[color(0)]]`, SPIR-V numbers outputs in declaration order. Role outputs are struct members with an explicit `[[vk::location(N)]]` (`shaders/include/color_slot.h.slang`); cooked output must be checked for locations, and in 3.4 for `InputAttachmentIndex` / `[[color(n)]]` inputs, rather than trusting source attributes.
* `SubpassInput` restrictions on Metal (2026.12.2 and 2026.19): fragment stage only; not in a `ParameterBlock` (E56109); a helper that calls `SubpassLoad` or takes the input as a parameter must be `[ForceInline]` (E56108). A `#if PIXEL_LOCAL` switch between `SubpassInput` and `Texture2D` under one name and binding compiles on both targets. Reading `[[color(N)]]` and writing `SV_TargetN` with different types is a Metal error. Subpass loads declare `StorageImageReadWithoutFormat` in SPIR-V. On Metal the pixel-local input has no texture binding (an entry-point argument); on Vulkan it is an `INPUT_ATTACHMENT` descriptor, so the shared `ResourceTable` (D21) must tolerate a binding absent or retyped per variant.

Each step: an implementer agent makes the change and raises questions or design improvements instead of guessing; the orchestrating session reviews the diff against the design and this plan; findings are fixed before the commit. Before each push, the local gates run in order: `dev/check_format.py`, `build.py --framework glfw --config Release --clangd`, `dev/check_tidy.py`, then the local test suites (macos and glfw/MoltenVK), run by a cheap-model subagent. CI runs on the PR.

## Findings

* Device features are chained onto `VkDeviceCreateInfo` with `ChainVkStructurePtr` (`VulkanCommon.h`). Ray tracing uses the individual 1.2 structs (`BufferDeviceAddress`, `DescriptorIndexing`), so a `VkPhysicalDeviceVulkan12Features` must never be added to the chain (VUID-VkDeviceCreateInfo-pNext-02830); likewise `VkPhysicalDeviceVulkan13Features` now carries `textureCompressionASTC_HDR`, so no standalone 1.3-promoted feature struct (dynamic rendering, sync2, ASTC HDR, ...) may be chained next to it (VUID-VkDeviceCreateInfo-pNext-06532). `dynamicRendering` and `synchronization2` are mandatory in 1.3, so the API version check is the only device requirement.
* Optional features: `VulkanContext::QueryOptionalDeviceFeatures()` sets `supports_*` flags (and pushes an optional extension's name) before device creation; `CreateLogicalDevice()` chains the matching feature structs. An optional extension must be compiled under `#ifdef VK_KHR_...` because the Android build uses the NDK's Vulkan headers, whose version is not pinned to the SDK's 1.4.350.
* Pixel-local read (Vulkan: `VK_KHR_dynamic_rendering_local_read`; Metal: framebuffer fetch on `MTLGPUFamilyApple2`) and unified image layouts are neither enabled nor queried: enabling an extension nothing uses is driver risk for no benefit. Phase 3 adds both with their first user.
* volk loads core 1.3 entry points (`vkCmdBeginRendering`, `vkCmdPipelineBarrier2`) in `volkLoadDevice` unconditionally; nothing else needs loading. ImGui's Vulkan backend defaults `ApiVersion` to the header version, so `VulkanUiHandler` sets it to 1.3.
* The ray tracing extension list still enables 1.2-promoted extensions: buffer device address (tied to `SetupMemoryAllocator` leaving `VmaAllocatorCreateInfo::vulkanApiVersion` at 1.0), and descriptor indexing, spirv_1_4 and float controls (left over from the 1.1 instance). Dropping them is a separate cleanup (TODO entry). `VK_KHR_shader_non_semantic_info` and `VK_KHR_format_feature_flags2` were removed because they are core in 1.3.
* `CheckDeviceExtensionSupport` also runs on the static `ray_tracing_extensions` list, which it mutates (portability subset), and `PickPhysicalDevice` appends that list to `device_extensions_` per candidate device before the suitability check, so duplicate names are possible on multi-GPU hosts or on MoltenVK (recorded in `docs/TODO.md`).
* The NRD cook (`shaders/nrd/cook/cook_nrd_shaders.py`, `docs/Denoiser.md`) downgrades NRD SPIR-V 1.5 to 1.4 and validates with `vulkan1.1spv1.4`, justified by a Vulkan 1.1 instance. Under 1.3 the downgrade is redundant (SPIR-V 1.5/1.6 are legal); docs/Denoiser.md states that the rewrite is not required, and the cook output is unchanged. A docs/TODO.md entry drops the downgrade and its validation target at the next NRD recook.
* Barrier API (`rhi/RHIBarrier.h`): `RHICommandContext::Barrier(span<const RHIImageBarrier>, span<const RHIMemoryBarrier>)` lowers one batch to one `vkCmdPipelineBarrier2` and records nothing on Metal. It is pure lowering and never touches `RHIImage` tracked state. `RHIAccess` is a flag set whose bits are the §4.2 accesses (no `PixelLocalRead` yet) plus `HostRead`; each bit implies its stage, except shader accesses (sampled, storage, uniform, AS read = ray query) whose stages come from `RHIShaderStageMask` (Vertex/Pixel/Compute). `RHIPipelineStage` survives only in the legacy `TransitionRequest`. An image barrier's `from_layout = Undefined` is the discard; there is no separate flag. Buffers and acceleration structures use global `RHIMemoryBarrier`s.
* Lowering details: `CopySrc`/`CopyDst` map to `TRANSFER` (not `COPY`), because blits (`GenerateMips`, `BlitToImage`) are transfer commands outside the COPY stage. Source access masks keep only write bits. `AccelerationStructureBuild` includes `SHADER_READ` at the build stage, the access Vulkan assigns to geometry and instance inputs.
* `RHIImage` tracks per subresource `{layout, access}`, where access is what the next barrier must wait for. `Transition` = `TrackTransition` (base class) + `Barrier`. It skips only a read-after-read in the same layout whose access bits and shader stages are already tracked; a read in a new stage emits a read→read barrier (valid through execution-dependency chaining) and widens the tracked readers; any write or layout change emits a barrier and resets the state to the new access. The source is the tracked access ∪ the write `after_stage` implies, so writes the tracker cannot see stay covered; `before_stage` Top/Bottom map to every shader stage. `Transition` is common code and Metal's `Barrier` records nothing, so Metal tracks the same state without recording.
* Writes the tracker cannot see: dispatches storing to an image without a preceding `Transition`. Render passes are no longer among them: attachment layouts come only from the tracker (see the rendering findings below), and a `ClearTexturePass` with a `StorageWrite` final layout ends with a `ColorWrite → StorageRead|StorageWrite` barrier for every shader stage, which orders the IBL cook's clear before its dispatches. The back-buffer render target's color image is re-pointed at the acquired swapchain image on every `AcquireImage` (`SyncWithSwapChain`), so `Begin` transitions and tracks the image being rendered and `EndFrame`'s `Present` transition waits for its `ColorWrite`.
* Acceleration structures: `VulkanTLAS::BuildInternal` emits `Build | Read(Pixel|Compute) → Build` before and `Build → Read(Pixel|Compute)` after the build. BLAS builds are one-shot submits on the same (only) queue, submitted before the frame command buffer; a pipeline barrier's first scope covers all earlier commands in submission order across submits, so the pre-build barrier orders BLAS → TLAS without a semaphore. BLAS geometry is host-visible and written before submit, so it needs no barrier.
* Remaining buffer hazards outside barrier scope: the TLAS instance buffer is one host-coherent buffer rewritten by `Update` while a previous in-flight frame's build may still read it; a dirty BLAS rebuild reuses its scratch buffer (`RecreateBuffer` keeps it when large enough) in a new one-shot submit with no barrier against the previous build's scratch writes. Copies record no barriers. `RHIBuffer::Upload` (the staging copy into a non-dynamic buffer) and `RHIBuffer::PartialUpdate` order their write after and before `RHIBuffer::GetUsageAccess`, the accesses derived from the destination's usage flags (`DeviceAddress` counts as a storage read; `AccelerationStructureStorage` adds nothing). A buffer the host reads needs `CopyDst → HostRead`, since fence waits do not make device writes host-visible: the graph records it right after the last live pass that uses a buffer marked `RenderGraph::ReadOnHost` (the screenshot readback), and `RHIImage::ReadToMemory` records it itself.
* The only sync1 `vkCmdPipelineBarrier` in first-party code is the android-emulator path for compressed images (see Learnings): the NRD inter-dispatch barrier goes through `RHICommandContext::Barrier`, and NRD pool initialization (raw `VkImage`s) uses `VkImageMemoryBarrier2` directly.
* Rendering API (`rhi/RHIRenderingInfo.h`): `RHIRenderingInfo` holds per-slot `RHIColorAttachment {image, resolve_image, mip_level, array_layer, load_op, store_op, clear_color, final_layout}`, one `RHIDepthAttachment` (clear depth 1), extent and sample count; `GetSignature()` gives the `RHIAttachmentSignature {color_formats per slot (PixelFormat::Count = unused), depth_format, samples}` pipelines compile against. A slot is the fragment output location on both backends (`colorAttachmentCount` = highest used slot + 1, gaps are null views and `VK_FORMAT_UNDEFINED`). `RHILoadOp`/`RHIStoreOp` are aliased as `RHIRenderPass::LoadOp/StoreOp`. `RHIRenderPass::GetRenderingInfo()` builds the info from the render target's current images at every `Begin`; the attribute keeps load/store, clear color and final layouts, and has no initial layouts. `RHICommandContext::BeginRenderPass` captures the info and its signature once on the pass (`GetActiveRenderingInfo()`, `GetActiveAttachmentSignature()`), and the backends and `DrawMesh` read them from there until the pass ends. `MaxNumColorAttachments` (8) backs `RHIRenderTarget::MaxNumColorImage`.
* Vulkan lowering (`VulkanRenderPass::Begin/End`): `Begin` batches the attachment transitions into one `Barrier` via `VulkanImage::TrackTransition` (exposed for batching), into `ColorOutput`/`DepthStencilOutput` from the tracked state, discarding (`TransitionRequest::discard`, an `Undefined` source layout) whenever the load op is not `Load`. Color sources include `COLOR_ATTACHMENT_OUTPUT`, which chains a swapchain image's first write with the acquire semaphore wait. `End` transitions each attachment whose `final_layout` differs from its attachment layout; the destination is the final layout's access (sampled or storage in every shader stage for `Read`/`StorageWrite`, `TRANSFER` for `TransferSrc`); otherwise the tracked state is already `{attachment layout, write}`. MSAA would render into the render target's hidden image and resolve through `resolveImageView` with `VK_RESOLVE_MODE_AVERAGE_BIT` (an integer format would need `SAMPLE_ZERO`), but no MSAA render target exists, so CI does not exercise that path. `RHICommandContext::BeginRenderPass` calls `BeginRenderPassInternal` before the pass becomes current and `EndRenderPass` clears it before `EndRenderPassInternal(pass)`, so these barriers satisfy `Barrier`'s outside-a-pass assertion. `BeginRenderPass` re-points a back-buffer pass at the current back buffer render target, which replaces the swapchain-recreation pass list.
* Viewport and scissor are dynamic state set once per pass at `Begin` from the pass extent through the tracked `SetViewportAndScissor`; draws no longer set them. Metal keeps its flipped viewport at `Begin`.
* PSOs: `RHIPipelineState::attachment_signature_` (optional) is the declared signature, set by `SetRenderPass`. Vulkan `VulkanForwardPipelineState::GetPipeline(signature)` compiles lazily into a per-PSO linear cache (`Compile` pre-builds the declared one) with `VkPipelineRenderingCreateInfo` and the signature's sample count (it was always 1); `DrawMesh` looks up the current pass's signature. Metal `Compile` requires the declared signature, because shader reflection comes from the first pipeline; further signatures compile at `Bind`. Shader modules and the create-info state live as long as the PSO, so lazy compiles need nothing re-set.
* ImGui on Vulkan uses `UseDynamicRendering` and compiles against the UI pass's own render target signature (the screen colour target: `screen_color_rt_`, `tone_mapping_rt_` or `composite_rt_`, never the back buffer), so colour format, depth format and samples match the pass by construction. After `ImGui_ImplVulkan_RenderDrawData`, `VulkanUiHandler::Render` calls `VulkanCommandContext::ResetCommandState`.
* Metal lowering (`MetalRenderPass::FillDescriptor`) sets `slice` from `array_layer` and the attachment clear color, so IBL cube-face clears hit their face and `ClearTexturePass` clear values (e.g. the GPU accumulator's `(0,0,0,0)`) apply on Metal, where they were `(0,0,0,1)`. Neither can change CI images: the cook is gated and the GPU pipeline runs locally only. Design §15 defects 6 (Metal clear colour and array layer) and 9 (stale tracked state after ImGui) are resolved.
* Barrier emission is not observable through the RHI, so no test case covers it; the 0.6 sync-validation gate is the check.
* A local compile check is possible despite no full build: `build_system/glfw/output/compile_commands.json` and the Vulkan SDK in `build_cache/` exist, so each changed file compiles with its database command plus `-fsyntax-only`, and `clang-tidy -p build_system/glfw/output <file>` (LLVM 22) runs. The flags include `-Werror -Wmissing-designated-field-initializers`: designated initializers must name every field that lacks a default member initializer.
* Command context (`rhi/RHICommandContext.h`): `RHICommandContext` records into one command buffer and owns the open render/compute pass (`GetCurrentRenderPass/ComputePass`) and every recording entry point: `Begin/EndRenderPass`, `Begin/EndComputePass`, `Barrier`, `DrawMesh`, `DispatchCompute`, and the transfers `CopyBuffer`, `CopyBufferToImage`, `CopyImageToBuffer`, `BlitImage` (image-to-image copy and mip generation had no callers and are gone). The checks live in the common non-virtual entry points, which call backend `*Internal` virtuals, so they fire on both backends: transfers assert outside any render or compute pass (`AssertOutsidePass`, also called by TLAS build/update and the MetalFX encode); `Barrier` rejects only render passes (NRD barriers between dispatches inside its compute pass) and ignores an empty batch. `RHIContext::GetCommandContext()` returns the context recording the open command buffer (the frame's, or the one `BeginCommandBuffer` opened), otherwise null. The recording API is gone from `RHIContext`; renderer call sites fetch the context once per pass, and `MeshRenderProxy::Render`, `RHIUiHandler::Render` and `RHINrdBackend::RunDispatches` take it as a parameter. `RHIImage`/`RHIBuffer` have no copy methods any more; the backend resource helpers take the Vulkan context or the Metal blit encoder / command buffer explicitly.
* Vulkan: `VulkanCommandContext` owns the `VkCommandBuffer` it records into and the `RHITrackedState` bind filters (formerly `VulkanContext::CommandState`); `Begin(command_buffer)` resets them. `VulkanContext` keeps one frame context, rebound to the frame-in-flight's command buffer, and every `OneShotCommandBufferScope` owns its own context and exposes its command buffer only through it (`BeginCommandBuffer` scopes; BLAS builds record their raw build command through it), so a one-shot buffer starts from clean tracked state and never shares filters with the frame recorded around it. The frame context ends before `vkEndCommandBuffer`. A recorded frame is always submitted, also when the surface is lost while it records (`RenderFramework::EndFrame` releases the render resources after the submit), so no context stays bound to a freed command buffer and no CPU-side state (tracked states, staged TLAS builds, timer queries) runs ahead of the GPU; `ReleaseRenderResources` asserts no frame is open. The scope's unused `use_external_if_possible` path is removed.
* Metal: `MetalCommandContext` owns the `MTLCommandBuffer` and the open render/compute encoder (`MetalRenderPass::Begin`/`MetalComputePass::Begin` return the encoder instead of keeping it). Each blit opens and ends its own encoder, and the common entry point asserts no pass encoder is open, so design §15 defect 5 fails in debug builds instead of encoding an overlapping encoder; no known caller copies inside a pass. One context serves the frame and one-shot buffers because Metal's `BeginCommandBuffer` already forbids overlapping command buffers; it has no bind filters. The mid-frame TLAS commit rebinds the same context through `SubmitCommandBuffer`/`BeginCommandBuffer`.
* Graph passes record only through their pass context: `RHIImage::Transition`, `Upload` and `UploadFaces` take the command context, and NRD and MetalFX pass theirs. `RHIContext::GetCommandContext()` serves only code outside graph passes: frame setup (`Renderer::ExecuteGraph`, `IblCookAccelerator`'s frame loop, the frame timers, Metal's end-of-frame handler and its mid-frame TLAS commit), and resource work recorded before the graph in the frame or in a `BeginCommandBuffer` scope: `RHIContext::CreateTexture`/`CreateTextureCube`/`GetOrCreateDummyTexture`, the IBL artifacts `ImageBasedLighting::InitRenderResources` applies, NRD's private textures, `RHIBuffer::Upload` of a non-dynamic buffer and `RHIBuffer::PartialUpdate`. The rule is enforced: `GetCommandContext()` is the common entry point over the backends' `GetCommandContextInternal`, and asserts (debug) while `RenderGraph::Execute` holds an `RHIContext::GraphExecutionScope` around its passes. Buffer uploads keep `RHIContext *` rather than a context: every upload inside a pass writes a dynamic buffer on the host, and the other callers (scene proxies, the bindless manager) have no context to pass, so a parameter would only move the `GetCommandContext()` call into each of them. `BeginCommandBuffer()` returns the context it opens; the code that opens a scope records through it (`IBLPass::Finalize`, `ReadToMemory`, the CPU cook's artifact apply, tests), and `IBLPass::ApplyArtifact` takes the context its upload records into. The descriptor-set cache stays in `VulkanDescriptorSetManager`.
* Pass timing (`rhi/RHIPass.h`): `RHIPass` is the common base of `RHIRenderPass` and `RHIComputePass` and owns the timing: one `RHITimer` per frame in flight when created with `need_timestamp` (`RHIRenderPass::Attribute::need_timestamp`, default false; `CreateComputePass(name, need_timestamp)` unchanged) and `RHIContext::SupportsPassTimestamps()`, otherwise none. `RHICommandContext::Begin/End*Pass` start the timer before `Begin*PassInternal` and stop it after `End*PassInternal`, so a pass's time covers its attachment barriers. `GetExecutionTime(frame_index)` is the slot's result read only at the pass's first begin in that slot per frame (`read_frame_` against `GetRenderedFrameCount()`), so a later begin never queries the timer its first begin just reset (VUID-vkGetQueryPoolResults-None-09401); a result not ready reads as -1, as do untimed and unsupported passes; a pass recorded twice in one frame reports its last run. `RHITimer::Begin/End` take the context. `PassTimingAggregator::AddStage` takes any `RHIPass`; no render pass opts in, so no consumer's numbers change. `VulkanComputePass` is gone (Vulkan creates a plain `RHIComputePass`).
* Vulkan timing: `SupportsPassTimestamps()` is `timestampValidBits > 0` on the universal queue's family (`VulkanContext::GetTimestampValidBits`); the frame timers follow it too. The tick difference is masked to the valid bits before scaling by `timestampPeriod`. Both timestamps stay at `BOTTOM_OF_PIPE` (reset and writes outside the rendering instance): the start waits for earlier work, so per-pass times partition the queue timeline instead of counting overlap twice, as a `TOP_OF_PIPE` start would.
* Metal timing: `SupportsPassTimestamps()` needs the `timestamp` counter set and `supportsCounterSampling:AtStageBoundary`; computed once when `MetalContext` is created; devices without it time nothing, and the timer's counter-set assert is unreachable on them. Render passes attach the sample buffer to `MTLRenderPassDescriptor.sampleBufferAttachments` with start/end of the vertex and fragment stages (4 samples); the time spans the earliest valid start to the latest valid end, ignoring `MTLCounterErrorValue`/zero samples from stages that did not run, and is -1 when none is valid (also when resolving fails, which used to leave the timer waiting forever). Compute keeps start/end of encoder. A timer registers one completed handler per command buffer: every run in it writes the same samples, so a second handler would find the first one's samples as "previous" and report 0 ms.
* Labels: Vulkan enables `VK_EXT_debug_utils` whenever validation is on or the instance lists it (loader, driver or implicit layer — the desktop loader always does, MoltenVK does), and drops it if the loader leaves its commands unresolved. `RHICommandContext` wraps every render and compute pass in a debug label (inside the timer bracket), the graph wraps every Copy and External pass in one through `RHICommandContext::DebugLabelScope`, Vulkan records them as `vkCmdBegin/EndDebugUtilsLabelEXT`, and `SetDebugInfo` names objects under the same rule. Metal records them as command buffer debug groups, pushed and popped only while no encoder is open, and also labels encoders and objects.
* The `pass_timestamps` test case (ubuntu-glfw, macos-glfw, macos-macos) records a clear timed by one pass twice, one timed by another pass once and an untimed one per frame and expects times once the slot returns, or none on a device without support; the pass recorded twice may measure 0 only when the pass recorded once does too. In CI, macos-macos (paravirtual Metal) reports pass timestamps unsupported, so the Metal timing path is not exercised; macos-glfw (MoltenVK) reports support but measures 0.0000 ms; only lavapipe measures real times. Metal render timing (the stage-boundary min/max, clear-only passes, and possibly stale samples left in a reused slot by stages that did not run) stays untested until an on-device run on a physical Apple GPU.
* Not done: Metal frame GPU time (`GPUEndTime - GPUStartTime` of the last command buffer) still undercounts when a TLAS build commits the frame mid-way; fixing it needs the first command buffer's start or a per-buffer sum, beyond this step (TODO entry).
* Descriptor sets (design §15 defect 3): `VulkanDescriptorSetManager::ReleaseDescriptorSet` queues an end-of-frame task that queues an end-of-render task, so the set returns to the free list (`ReturnDescriptorSet`) at `BeginFrame` of the releasing frame's slot, after that slot's fence wait, `max_frames_in_flight` frames later. A release outside a frame (one-shot scope, deferred deletion in `BeginFrame`) waits for the next `EndFrame` first, so it is never early. Going through the end-of-frame queue also keeps `RHIContext::Cleanup` safe: it clears `end_of_render_tasks_` (the outer vector) before `FlushDeferredDeletions` destroys PSOs, so a direct `EnqueueEndOfRenderTasks` there would index an empty vector.
* Bindless flush (defect 4): `VulkanDescriptorSet::Bind` calls `UpdateDirtyResourceArrays` before requesting its set, so every draw and dispatch sees flushed arrays; `VulkanRenderPass::Begin` no longer flushes. Two ordering bugs are fixed with it: a newly requested set's full write calls `FinishUpdate` on its arrays, which cleared their dirty entries before other sets using them had been patched (flushing first avoids it); and `VulkanResourceArray::WriteDescriptorForDirtyResource` cleared the dirty indices itself, so `UpdateDirtyResourceArrays` patched only the first set using an array (it is const now; the manager's `FinishUpdate` after the loop clears them). Updating sets already bound in the open command buffer or in flight relies on `UPDATE_AFTER_BIND`, which bindless bindings carry only when hardware ray tracing is supported; the bindless arrays are updated during scene proxy updates before any pass records, so without ray tracing nothing changes relative to the render-pass flush. Metal patches its argument buffer inside `MetalResourceArray::Bind` for render and compute encoders alike, so it needed nothing; it writes that shared buffer in place while earlier frames may still read it (not changed here).
* Sync validation knob: `validate_sync` (RHIConfig `enable_sync_validation`, default false) adds `VkLayerSettingEXT{"VK_LAYER_KHRONOS_validation", "validate_sync", BOOL32, true}` to a `VkLayerSettingsCreateInfoEXT` that is now built on every platform (MoltenVK settings join it on macOS; guarded by `#ifdef VK_EXT_layer_settings` for NDK headers). The layer reads the struct without `VK_EXT_layer_settings` being enabled, and lists it as allowed in `VkInstanceCreateInfo::pNext` (`VkValidationFeaturesEXT` is deprecated in the layer). `VulkanContext::enable_sync_validation_` is set only when the setting is added, exposed as `RHIContext::IsSyncValidationActive()`.
* Verdict: the debug messenger counts error-severity messages of the validation type (`pUserData` is `VulkanContext::validation_error_count_`) and logs every error at Error ("validation error!"); warnings log at Warn as "validation warning!" (they used to say "error" too). `RHIContext::GetValidationErrorCount()` returns the count, or nullopt without an active layer (Metal always). `TestCase::Tick` fails the case once the count exceeds what the case accepted (`AcceptValidationErrors(count)`, for cases that provoke errors), and fails a `validate_sync` run unless `IsSyncValidationActive()`. This applies to every test run with the layer active: the packaged config sets `validation: true`; macos-glfw CI already had the layer active through `run.py`, and the android emulator cell already ships it (`setup_android_validation` puts it in jniLibs). macos-glfw's only reported message was 3 leaked `VkSampler`s at `vkDestroyDevice` after `scene_load_failure` passed (after the verdict, so it does not fail; a pre-existing leak); android logged `VUID-vkAcquireNextImageKHR-semaphore-01779` twice during `surface_loss_recovery`, which the new check would fail (fixed below).
* CI gate: registry cases `forward_sync_validation`, `deferred_sync_validation`, `gpu_sync_validation` (test_case `screenshot`, `--validation true --validate_sync true`, gpu with `--max_spp 4`, no evaluator) and the negative `sync_validation_hazard` run on `ubuntu-glfw-release`. `sync_validation_hazard` records two raw `vkCmdCopyBuffer`s into one buffer, with no barrier between them, in its own command buffer, expects at least one new error, and accepts exactly that many, which proves the setting took effect and the gate can fail. That test job restores `./build_cache` (same key as the build jobs' setup-environment, restore-only) and registers the SDK 1.4.350 layer through `VK_ADD_LAYER_PATH` with a manifest copy in `$RUNNER_TEMP` whose `library_path` is absolute (the SDK manifest names the library bare; `LD_LIBRARY_PATH` would also swap the cell's loader for the SDK's); a missing library fails the step. Checked locally: the copied manifest loads the layer through the system loader on lavapipe. The distro `vulkan-validationlayers` (1.3.275 on noble) was not used: it predates headers the app is built against and features lavapipe exposes. Consequence: every case on that cell now runs under core validation. Run 536's ubuntu-glfw log shows llvmpipe (LLVM 20.1.2) and `effective pipeline: Gpu`, so `gpu_sync_validation` runs the path tracer, with `UPDATE_AFTER_BIND`/`PARTIALLY_BOUND` bindless available. That also makes `gpu_render_static`'s "no hosted runner exposes ray tracing" stale for the lavapipe cells: a coverage opportunity, out of scope here.
* Hazards fixed by reading: `VulkanBuffer::CopyToBuffer` (hence `RHIBuffer::Upload`) now waits for the destination's usage accesses before the copy (WAR/WAW); `RHIBuffer::PartialUpdate` does the same before its dispatch; `VulkanBLAS::Build` puts a build→build barrier before the build so a rebuild's reused scratch waits for the previous build submit. Not fixed: the TLAS instance buffer is still one host-coherent buffer rewritten while earlier frames' builds may read it (host writes are invisible to sync validation; the fix needs per-frame instance storage with full rewrites); the Metal argument buffer in-place patch (same class). Both are TODO entries.
* Acquire semaphores (android `surface_loss_recovery`, VUID-vkAcquireNextImageKHR-semaphore-01779): `VulkanContext::BeginFrame` advanced `next_acquire_semaphore_index_` on every acquire attempt, so repeated failed acquires (`VK_ERROR_SURFACE_LOST_KHR`, `OUT_OF_DATE`) while the surface was gone cycled the ring onto a semaphore an in-flight frame still waited on. It advances only on `VK_SUCCESS`/`VK_SUBOPTIMAL_KHR` now; a failed acquire performs no signal operation (the layer records the signal only on success), so its semaphore is reused as is.

## Learnings

* Metal files (`.mm`) compile only in the macOS CI jobs; review their const-correctness and API use by hand before pushing (a const pointer to an image calling non-const `GetDefaultView` broke the macOS builds once).

* When a change breaks an existing capability on some device, make the change work there, or fall back to the old behavior in that specific case. Never drop an existing feature from the support matrix to accommodate a new one: maximize feature coverage.
* CI toolchains are unpinned (`aminya/setup-cpp` installs the latest LLVM). clang-cl maps `-Wall` to `-Weverything`, so each new LLVM release can add warnings that fail only the Windows builds; `-Wpadded` and `-Wnrvo` are opted out in `CMakeLists.txt` for that reason.
* Android emulator (llvmpipe over gfxstream) screenshots are deterministic across CI runs of the same commit: two runs of step 0.2 gave identical FLIP (forward 0.0264, deferred 0.0404). A FLIP change on that cell is a real behavior change, not noise; `primitive_move` is the exception and varies between runs (0.018–0.026).
* CI runners are shared: cancel a run as soon as it has a failure that settles the question, and cancel runs superseded by a newer push (`mcp__github__actions_run_trigger` `cancel_workflow_run`). Push notes-only commits with `[skip ci]`.
* The android emulator (gfxstream over host lavapipe) advertises ASTC LDR and emulates it by decoding on the GPU when it intercepts a sync1 `vkCmdPipelineBarrier`; its `vkCmdPipelineBarrier2` skips the decode (fixed in gfxstream 9068c3aa). On that device only (`VulkanContext::CompressedImageBarriersNeedSync1`: android + llvmpipe), `VulkanCommandContext::Barrier` records image barriers on compressed-format images with sync1; every other barrier, and every barrier on other devices, uses sync2. Without it the ASTC material textures stay undecoded and the glTF models render almost black.
* First sync-validation CI run (ubuntu-glfw lavapipe): forward and deferred run clean under synchronization validation, and `sync_validation_hazard` confirms the gate reports a real hazard. `gpu_sync_validation` exposed the path tracer sampling its scene texture in `GENERAL` on frames without a dispatch (VUID-vkCmdDraw-None-09600), fixed in `GPURenderer::Render`. Three `VkSampler`s leak at `vkDestroyDevice` (reported after the verdict, so no case fails on it); the leak is still open (TODO entry).
* Physical Apple GPU (M5 Max, macOS 27, probe `tmp/metal_timing_probe/probe.mm`): a compute encoder that dispatches nothing is skipped and never writes its stage-boundary samples — zero in a new sample buffer, and the previous run's timestamps, bit-identical, in a reused one; render encoders sample both stages even when they only clear or draw nothing. `render_graph_pass_timing`'s empty Trace pass therefore never got a time on macos-macos with real timestamps, and a compute pass that dispatches nothing in some frame would have reported a stale time. `MetalTimer` now keeps each buffer's last resolved samples and treats a sample equal to it (or zero) as unwritten; a pass none of whose stages ran reports 0 ms (Vulkan measures ~0.002 ms for the same pass), `MTLCounterErrorValue` still -1. The legacy `MTLCounterSampleBuffer` path works on macOS 27 (wgpu reports all-zero timestamps on macOS 26 Metal 4, gfx-rs/wgpu#9414; not seen here).
