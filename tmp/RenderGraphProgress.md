# Render Graph Progress

Working log for [RenderGraphDesign.md](RenderGraphDesign.md). Records the plan per phase, what landed, findings and learnings. The design doc stays the source of truth for intent; deviations are recorded here with the reason.

## Decisions

* Vulkan 1.3 core is the minimum (dynamic rendering + synchronization2 required). `VK_KHR_dynamic_rendering_local_read` and `VK_KHR_unified_image_layouts` are optional capabilities.
* Metal is changed alongside Vulkan in each step; Metal correctness is gated by the macOS CI jobs (no local Metal build).
* Phase 0 is implemented in full.
* Deviations carried into Phase 1: `RHIAttachmentSignature` has no per-slot write mask (§7.1), and `StoreOp::None` still lowers to `DONT_CARE` rather than `STORE_OP_NONE` (§6.5); both belong with load/store inference and pass merging in Phase 1.

Deviations from the design, from reading Phase 0 code:

* Imports and transients are seeded from the physical image's tracked `{layout, access}` and the graph writes state through to the tracker per pass (design §4.1, §6.4, §6.6 updated). A transient seeded from `Undefined` with no source access would race the previous frame's use of the pooled image, and the swapchain's first write must chain to the acquire wait as `VulkanRenderPass::Begin` does today.
* The graph reuses Phase 0's `RHIAccess`/`RHIShaderStageMask`/`RHIImageLayout` inside accesses; the builder methods are the §4.2 vocabulary.
* `Present` needs no access: `EndFrame` transitions the back buffer from tracked state.
* `RHIImageLayout` has no read-only depth layout; `DepthTest` uses the depth attachment layout until a pass samples and tests the same depth.
* Graph validation and the External-pass contract (each declared image left in its declared state) abort in every build, because `ASSERT` compiles out of the Release builds CI runs.
* Shader variants have no Phase 1 user; they arrive with pixel-local reads in Phase 3.
* The two Phase 0 deviations (per-slot write mask, `StoreOp::None` lowering) have no user without merging and move to Phase 3.

## Workflow

Each step: an implementer agent makes the change and raises questions or design improvements instead of guessing; the orchestrating session reviews the diff against the design and this plan; findings are fixed before the commit. Nothing is built or run locally: each step is pushed to the `render-graph` branch and its PR, and CI (builds on every platform, tidy, screenshot tests) is the validation.

## Findings

* Device features are chained onto `VkDeviceCreateInfo` with `ChainVkStructurePtr` (`VulkanCommon.h`). Ray tracing uses the individual 1.2 structs (`BufferDeviceAddress`, `DescriptorIndexing`), so a `VkPhysicalDeviceVulkan12Features` must never be added to the chain (VUID-VkDeviceCreateInfo-pNext-02830); likewise `VkPhysicalDeviceVulkan13Features` now carries `textureCompressionASTC_HDR`, so no standalone 1.3-promoted feature struct (dynamic rendering, sync2, ASTC HDR, ...) may be chained next to it (VUID-VkDeviceCreateInfo-pNext-06532). `dynamicRendering` and `synchronization2` are mandatory in 1.3, so the API version check is the only device requirement.
* Optional capabilities: `VulkanContext::QueryOptionalDeviceFeatures()` sets `supports_*` flags and pushes the extension names before device creation; `CreateLogicalDevice()` chains the matching feature structs. Both optional extensions are compiled under `#ifdef VK_KHR_...` because the Android build uses the NDK's Vulkan headers, whose version is not pinned to the SDK's 1.4.350.
* RHI queries: `RHIContext::SupportsPixelLocalRead()` (Vulkan: `VK_KHR_dynamic_rendering_local_read`; Metal: `MTLGPUFamilyApple2`) and `RHIContext::SupportsUnifiedImageLayouts()` (Metal: false).
* volk loads core 1.3 entry points (`vkCmdBeginRendering`, `vkCmdPipelineBarrier2`) in `volkLoadDevice` unconditionally; nothing else needs loading. ImGui's Vulkan backend defaults `ApiVersion` to the header version, so `VulkanUiHandler` sets it to 1.3.
* The ray tracing extension list still enables 1.2-promoted extensions: buffer device address (tied to `SetupMemoryAllocator` leaving `VmaAllocatorCreateInfo::vulkanApiVersion` at 1.0), and descriptor indexing, spirv_1_4 and float controls (left over from the 1.1 instance). Dropping them is a separate cleanup. `VK_KHR_shader_non_semantic_info` and `VK_KHR_format_feature_flags2` were removed because they are core in 1.3.
* `CheckDeviceExtensionSupport` also runs on the static `ray_tracing_extensions` list, which it mutates (portability subset), and `PickPhysicalDevice` appends that list to `device_extensions_` per candidate device before the suitability check, so duplicate names are possible on multi-GPU hosts or on MoltenVK (recorded in `docs/TODO.md`).
* The NRD cook (`shaders/nrd/cook/cook_nrd_shaders.py`, `docs/Denoiser.md`) downgrades NRD SPIR-V 1.5 to 1.4 and validates with `vulkan1.1spv1.4`, justified by a Vulkan 1.1 instance. Under 1.3 the downgrade is redundant (SPIR-V 1.5/1.6 are legal); the docs now state the rewrite without the 1.1 justification, and the cook output is unchanged. Removing the downgrade needs a recook.
* Barrier API (`rhi/RHIBarrier.h`): `RHICommandContext::Barrier(span<const RHIImageBarrier>, span<const RHIMemoryBarrier>)` lowers one batch to one `vkCmdPipelineBarrier2` and records nothing on Metal. It is pure lowering and never touches `RHIImage` tracked state. `RHIAccess` is a flag set whose bits are the §4.2 accesses (no `PixelLocalRead` yet) plus `HostRead`; each bit implies its stage, except shader accesses (sampled, storage, uniform, AS read = ray query) whose stages come from `RHIShaderStageMask` (Vertex/Pixel/Compute). `RHIPipelineStage` survives only in the legacy `TransitionRequest`. An image barrier's `from_layout = Undefined` is the discard; there is no separate flag. Buffers and acceleration structures use global `RHIMemoryBarrier`s.
* Lowering details: `CopySrc`/`CopyDst` map to `TRANSFER` (not `COPY`), because blits (`GenerateMips`, `BlitToImage`) are transfer commands outside the COPY stage. Source access masks keep only write bits. `AccelerationStructureBuild` includes `SHADER_READ` at the build stage, the access Vulkan assigns to geometry and instance inputs.
* `RHIImage` tracks per subresource `{layout, access}`, where access is what the next barrier must wait for. `Transition` = `TrackTransition` (base class) + `Barrier`. It skips only a read-after-read in the same layout whose access bits and shader stages are already tracked; a read in a new stage emits a read→read barrier (valid through execution-dependency chaining) and widens the tracked readers; any write or layout change emits a barrier and resets the state to the new access. The source is the tracked access ∪ the write `after_stage` implies, so writes the tracker cannot see stay covered; `before_stage` Top/Bottom map to every shader stage. Metal's `Transition` stays empty, so its tracked state never changes.
* Writes the tracker cannot see: dispatches storing to an image without a preceding `Transition`. Render passes are no longer among them: attachment layouts come only from the tracker (see the rendering findings below), and a `ClearTexturePass` with a `StorageWrite` final layout ends with a `ColorWrite → StorageRead|StorageWrite` barrier for every shader stage, which orders the IBL cook's clear before its dispatches. The back-buffer render target's color image is re-pointed at the acquired swapchain image on every `AcquireImage` (`SyncWithSwapChain`), so `Begin` transitions and tracks the image being rendered and `EndFrame`'s `Present` transition waits for its `ColorWrite`.
* Acceleration structures: `VulkanTLAS::BuildInternal` emits `Build | Read(Pixel|Compute) → Build` before and `Build → Read(Pixel|Compute)` after the build. BLAS builds are one-shot submits on the same (only) queue, submitted before the frame command buffer; a pipeline barrier's first scope covers all earlier commands in submission order across submits, so the pre-build barrier orders BLAS → TLAS without a semaphore. BLAS geometry is host-visible and written before submit, so it needs no barrier.
* Remaining buffer hazards outside barrier scope: the TLAS instance buffer is one host-coherent buffer rewritten by `Update` while a previous in-flight frame's build may still read it; `RHIBuffer::Upload` into a non-dynamic buffer has no WAR barrier before its copy; a dirty BLAS rebuild reuses its scratch buffer (`RecreateBuffer` keeps it when large enough) in a new one-shot submit with no barrier against the previous build's scratch writes. `VulkanBuffer::CopyToBuffer` and `RHIBuffer::PartialUpdate` order their write before `RHIBuffer::GetUsageAccess`, the accesses derived from the destination's usage flags (`DeviceAddress` counts as a storage read; `AccelerationStructureStorage` adds nothing); image `CopyToBuffer` (readback) adds `CopyDst → HostRead`, since fence waits do not make device writes host-visible.
* The only sync1 `vkCmdPipelineBarrier` in first-party code is the android-emulator path for compressed images (see Learnings): the NRD inter-dispatch barrier goes through `RHICommandContext::Barrier`, and NRD pool initialization (raw `VkImage`s) uses `VkImageMemoryBarrier2` directly.
* Rendering API (`rhi/RHIRenderingInfo.h`): `RHIRenderingInfo` holds per-slot `RHIColorAttachment {image, resolve_image, mip_level, array_layer, load_op, store_op, clear_color, final_layout}`, one `RHIDepthAttachment` (clear depth 1), extent and sample count; `GetSignature()` gives the `RHIAttachmentSignature {color_formats per slot (PixelFormat::Count = unused), depth_format, samples}` pipelines compile against. A slot is the fragment output location on both backends (`colorAttachmentCount` = highest used slot + 1, gaps are null views and `VK_FORMAT_UNDEFINED`). `RHILoadOp`/`RHIStoreOp` are aliased as `RHIRenderPass::LoadOp/StoreOp`. `RHIRenderPass::GetRenderingInfo()` builds the info from the render target's current images at every `Begin`; the attribute keeps load/store, clear color and final layouts, and has no initial layouts. `RHICommandContext::BeginRenderPass` captures the info and its signature once on the pass (`GetActiveRenderingInfo()`, `GetActiveAttachmentSignature()`), and the backends and `DrawMesh` read them from there until the pass ends. `MaxNumColorAttachments` (8) backs `RHIRenderTarget::MaxNumColorImage`.
* Vulkan lowering (`VulkanRenderPass::Begin/End`): `Begin` batches the attachment transitions into one `Barrier` via `VulkanImage::TrackTransition` (exposed for batching), into `ColorOutput`/`DepthStencilOutput` from the tracked state, discarding (`TransitionRequest::discard`, an `Undefined` source layout) whenever the load op is not `Load`. Color sources include `COLOR_ATTACHMENT_OUTPUT`, which chains a swapchain image's first write with the acquire semaphore wait. `End` transitions each attachment whose `final_layout` differs from its attachment layout; the destination is the final layout's access (sampled or storage in every shader stage for `Read`/`StorageWrite`, `TRANSFER` for `TransferSrc`); otherwise the tracked state is already `{attachment layout, write}`. MSAA would render into the render target's hidden image and resolve through `resolveImageView` with `VK_RESOLVE_MODE_AVERAGE_BIT` (an integer format would need `SAMPLE_ZERO`), but no MSAA render target exists, so CI does not exercise that path. `RHICommandContext::BeginRenderPass` calls `BeginRenderPassInternal` before the pass becomes current and `EndRenderPass` clears it before `EndRenderPassInternal(pass)`, so these barriers satisfy `Barrier`'s outside-a-pass assertion. `BeginRenderPass` re-points a back-buffer pass at the current back buffer render target, which replaces the swapchain-recreation pass list.
* Viewport and scissor are dynamic state set once per pass at `Begin` from the pass extent through the tracked `SetViewportAndScissor`; draws no longer set them. Metal keeps its flipped viewport at `Begin`.
* PSOs: `RHIPipelineState::attachment_signature_` (optional) is the declared signature, set by `SetRenderPass`. Vulkan `VulkanForwardPipelineState::GetPipeline(signature)` compiles lazily into a per-PSO linear cache (`Compile` pre-builds the declared one) with `VkPipelineRenderingCreateInfo` and the signature's sample count (it was always 1); `DrawMesh` looks up the current pass's signature. Metal `Compile` requires the declared signature, because shader reflection comes from the first pipeline; further signatures compile at `Bind`. Shader modules and the create-info state live as long as the PSO, so lazy compiles need nothing re-set.
* ImGui on Vulkan uses `UseDynamicRendering` and compiles against the UI pass's own render target signature (the screen colour target: `screen_color_rt_`, `tone_mapping_rt_` or `composite_rt_`, never the back buffer), so colour format, depth format and samples match the pass by construction. After `ImGui_ImplVulkan_RenderDrawData`, `VulkanUiHandler::Render` calls `VulkanCommandContext::ResetCommandState`.
* Metal lowering (`MetalRenderPass::FillDescriptor`) sets `slice` from `array_layer` and the attachment clear color, so IBL cube-face clears hit their face and `ClearTexturePass` clear values (e.g. the GPU accumulator's `(0,0,0,0)`) apply on Metal, where they were `(0,0,0,1)`. Neither can change CI images: the cook is gated and the GPU pipeline runs locally only. Design §15 defects 6 (Metal clear colour and array layer) and 9 (stale tracked state after ImGui) are resolved.
* Barrier emission is not observable through the RHI, so no test case covers it; the 0.6 sync-validation gate is the check.
* A local compile check is possible despite no full build: `build_system/glfw/output/compile_commands.json` and the Vulkan SDK in `build_cache/` exist, so each changed file compiles with its database command plus `-fsyntax-only`, and `clang-tidy -p build_system/glfw/output <file>` (LLVM 22) runs. The flags include `-Werror -Wmissing-designated-field-initializers`: designated initializers must name every field that lacks a default member initializer.
* Command context (`rhi/RHICommandContext.h`): `RHICommandContext` records into one command buffer and owns the open render/compute pass (`GetCurrentRenderPass/ComputePass`) and every recording entry point: `Begin/EndRenderPass`, `Begin/EndComputePass`, `Barrier`, `DrawMesh`, `DispatchCompute`, and the transfers `CopyBuffer`, `CopyBufferToImage`, `CopyImageToBuffer`, `BlitImage` (image-to-image copy and mip generation had no callers and are gone). The checks live in the common non-virtual entry points, which call backend `*Internal` virtuals, so they fire on both backends: transfers assert outside any render or compute pass (`AssertOutsidePass`, also called by TLAS build/update and the MetalFX encode); `Barrier` rejects only render passes (NRD barriers between dispatches inside its compute pass) and ignores an empty batch. `RHIContext::GetCommandContext()` returns the context recording the open command buffer (the frame's, or the one `BeginCommandBuffer` opened), otherwise null. The recording API is gone from `RHIContext`; renderer call sites fetch the context once per pass, and `MeshRenderProxy::Render`, `RHIUiHandler::Render` and `RHINrdBackend::RunDispatches` take it as a parameter. `RHIImage`/`RHIBuffer` have no copy methods any more; the backend resource helpers take the Vulkan context or the Metal blit encoder / command buffer explicitly.
* Vulkan: `VulkanCommandContext` owns the `VkCommandBuffer` it records into and the `RHITrackedState` bind filters (formerly `VulkanContext::CommandState`); `Begin(command_buffer)` resets them. `VulkanContext` keeps one frame context, rebound to the frame-in-flight's command buffer, and every `OneShotCommandBufferScope` owns its own context and exposes its command buffer only through it (`BeginCommandBuffer` scopes; BLAS builds record their raw build command through it), so a one-shot buffer starts from clean tracked state and never shares filters with the frame recorded around it. The frame context ends before `vkEndCommandBuffer`, and `ReleaseRenderResources` ends it when surface loss skips `EndFrame`, so no context stays bound to a freed command buffer. The scope's unused `use_external_if_possible` path is removed.
* Metal: `MetalCommandContext` owns the `MTLCommandBuffer` and the open render/compute encoder (`MetalRenderPass::Begin`/`MetalComputePass::Begin` return the encoder instead of keeping it). Each blit opens and ends its own encoder, and the common entry point asserts no pass encoder is open, so design §15 defect 5 fails in debug builds instead of encoding an overlapping encoder; no known caller copies inside a pass. One context serves the frame and one-shot buffers because Metal's `BeginCommandBuffer` already forbids overlapping command buffers; it has no bind filters. The mid-frame TLAS commit rebinds the same context through `SubmitCommandBuffer`/`BeginCommandBuffer`.
* Still reached through `GetCommandContext()` instead of an explicit parameter: resource-side recording (`RHIImage::Transition`, `RHIImage::Upload`, `RHIBuffer::Upload`/`PartialUpdate`, `ReadToMemory`, TLAS build/update). The descriptor-set cache stays in `VulkanDescriptorSetManager`. Phase 1 hands the context to execute lambdas and turns uploads/readback into Copy passes; parallel recording (Phase 4) additionally needs per-context descriptor caches and a context per frame in flight.
* Pass timing (`rhi/RHIPass.h`): `RHIPass` is the common base of `RHIRenderPass` and `RHIComputePass` and owns the timing: one `RHITimer` per frame in flight when created with `need_timestamp` (`RHIRenderPass::Attribute::need_timestamp`, default false; `CreateComputePass(name, need_timestamp)` unchanged) and `RHIContext::SupportsPassTimestamps()`, otherwise none. `RHICommandContext::Begin/End*Pass` start the timer before `Begin*PassInternal` and stop it after `End*PassInternal`, so a pass's time covers its attachment barriers. `GetExecutionTime(frame_index)` is the slot's result read only at the pass's first begin in that slot per frame (`read_frame_` against `GetRenderedFrameCount()`), so a later begin never queries the timer its first begin just reset (VUID-vkGetQueryPoolResults-None-09401); a result not ready reads as -1, as do untimed and unsupported passes; a pass recorded twice in one frame reports its last run. `RHITimer::Begin/End` take the context. `PassTimingAggregator::AddStage` takes any `RHIPass`; no render pass opts in, so no consumer's numbers change. `VulkanComputePass` is gone (Vulkan creates a plain `RHIComputePass`).
* Vulkan timing: `SupportsPassTimestamps()` is `timestampValidBits > 0` on the universal queue's family (`VulkanContext::GetTimestampValidBits`); the frame timers follow it too. The tick difference is masked to the valid bits before scaling by `timestampPeriod`. Both timestamps stay at `BOTTOM_OF_PIPE` (reset and writes outside the rendering instance): the start waits for earlier work, so per-pass times partition the queue timeline instead of counting overlap twice, as a `TOP_OF_PIPE` start would.
* Metal timing: `SupportsPassTimestamps()` needs the `timestamp` counter set and `supportsCounterSampling:AtStageBoundary`; queried once and cached in `MetalContext`; devices without it time nothing, and the timer's counter-set assert is unreachable on them. Render passes attach the sample buffer to `MTLRenderPassDescriptor.sampleBufferAttachments` with start/end of the vertex and fragment stages (4 samples); the time spans the earliest valid start to the latest valid end, ignoring `MTLCounterErrorValue`/zero samples from stages that did not run, and is -1 when none is valid (also when resolving fails, which used to leave the timer waiting forever). Compute keeps start/end of encoder.
* Labels: Vulkan enables `VK_EXT_debug_utils` whenever validation is on or the instance lists it (loader, driver or implicit layer — the desktop loader always does, MoltenVK does), and drops it if the loader leaves its commands unresolved. `VulkanCommandContext` wraps every render and compute pass in `vkCmdBegin/EndDebugUtilsLabelEXT` (inside the timer bracket), and `SetDebugInfo` names objects under the same rule. Metal already labels encoders and objects.
* The `pass_timestamps` test case (ubuntu-glfw, macos-glfw, macos-macos) records a timed clear pass twice and an untimed one once per frame and expects a time (0 accepted) once the slot returns, or none on a device without support. In CI, macos-macos (paravirtual Metal) reports pass timestamps unsupported, so the Metal timing path is not exercised; macos-glfw (MoltenVK) reports support but measures 0.0000 ms; only lavapipe measures real times. Metal render timing (the stage-boundary min/max, clear-only passes, and possibly stale samples left in a reused slot by stages that did not run) stays untested until an on-device run on a physical Apple GPU.
* Not done: Metal frame GPU time (`GPUEndTime - GPUStartTime` of the last command buffer) still undercounts when a TLAS build commits the frame mid-way; fixing it needs the first command buffer's start or a per-buffer sum, beyond this step.
* Descriptor sets (design §15 defect 3): `VulkanDescriptorSetManager::ReleaseDescriptorSet` queues an end-of-frame task that queues an end-of-render task, so the set returns to the free list (`ReturnDescriptorSet`) at `BeginFrame` of the releasing frame's slot, after that slot's fence wait, `max_frames_in_flight` frames later. A release outside a frame (one-shot scope, deferred deletion in `BeginFrame`) waits for the next `EndFrame` first, so it is never early. Going through the end-of-frame queue also keeps `RHIContext::Cleanup` safe: it clears `end_of_render_tasks_` (the outer vector) before `FlushDeferredDeletions` destroys PSOs, so a direct `EnqueueEndOfRenderTasks` there would index an empty vector.
* Bindless flush (defect 4): `VulkanDescriptorSet::Bind` calls `UpdateDirtyResourceArrays` before requesting its set, so every draw and dispatch sees flushed arrays; `VulkanRenderPass::Begin` no longer flushes. Two ordering bugs are fixed with it: a newly requested set's full write calls `FinishUpdate` on its arrays, which cleared their dirty entries before other sets using them had been patched (flushing first avoids it); and `VulkanResourceArray::WriteDescriptorForDirtyResource` cleared the dirty indices itself, so `UpdateDirtyResourceArrays` patched only the first set using an array (it is const now; the manager's `FinishUpdate` after the loop clears them). Updating sets already bound in the open command buffer or in flight relies on `UPDATE_AFTER_BIND`, which bindless bindings carry only when hardware ray tracing is supported; the bindless arrays are updated during scene proxy updates before any pass records, so without ray tracing nothing changes relative to the render-pass flush. Metal patches its argument buffer inside `MetalResourceArray::Bind` for render and compute encoders alike, so it needed nothing; it writes that shared buffer in place while earlier frames may still read it (not changed here).
* Sync validation knob: `validate_sync` (RHIConfig `enable_sync_validation`, default false) adds `VkLayerSettingEXT{"VK_LAYER_KHRONOS_validation", "validate_sync", BOOL32, true}` to a `VkLayerSettingsCreateInfoEXT` that is now built on every platform (MoltenVK settings join it on macOS; guarded by `#ifdef VK_EXT_layer_settings` for NDK headers). The layer reads the struct without `VK_EXT_layer_settings` being enabled, and lists it as allowed in `VkInstanceCreateInfo::pNext` (`VkValidationFeaturesEXT` is deprecated in the layer). `VulkanContext::enable_sync_validation_` is set only when the setting is added, exposed as `RHIContext::IsSyncValidationActive()`.
* Verdict: the debug messenger counts error-severity messages of the validation type (`pUserData` is `VulkanContext::validation_error_count_`) and logs every error at Error ("validation error!"); warnings log at Warn as "validation warning!" (they used to say "error" too). `RHIContext::GetValidationErrorCount()` returns the count, or nullopt without an active layer (Metal always). `TestCase::Tick` fails the case once the count exceeds what the case accepted (`AcceptValidationErrors(count)`, for cases that provoke errors), and fails a `validate_sync` run unless `IsSyncValidationActive()`. This applies to every test run with the layer active: the packaged config sets `validation: true`; macos-glfw CI already had the layer active through `run.py`, and the android emulator cell already ships it (`setup_android_validation` puts it in jniLibs). macos-glfw's only reported message was 3 leaked `VkSampler`s at `vkDestroyDevice` after `scene_load_failure` passed (after the verdict, so it does not fail; a pre-existing leak); android logged `VUID-vkAcquireNextImageKHR-semaphore-01779` twice during `surface_loss_recovery`, which the new check would fail (fixed below).
* CI gate: registry cases `forward_sync_validation`, `deferred_sync_validation`, `gpu_sync_validation` (test_case `screenshot`, `--validation true --validate_sync true`, gpu with `--max_spp 4`, no evaluator) and the negative `sync_validation_hazard` run on `ubuntu-glfw-release`. `sync_validation_hazard` records two raw `vkCmdCopyBuffer`s into one buffer (bypassing `RHICommandContext::CopyBuffer` and its barriers) in its own command buffer, expects at least one new error, and accepts exactly that many, which proves the setting took effect and the gate can fail. That test job restores `./build_cache` (same key as the build jobs' setup-environment, restore-only) and registers the SDK 1.4.350 layer through `VK_ADD_LAYER_PATH` with a manifest copy in `$RUNNER_TEMP` whose `library_path` is absolute (the SDK manifest names the library bare; `LD_LIBRARY_PATH` would also swap the cell's loader for the SDK's); a missing library fails the step. Checked locally: the copied manifest loads the layer through the system loader on lavapipe. The distro `vulkan-validationlayers` (1.3.275 on noble) was not used: it predates headers the app is built against and features lavapipe exposes. Consequence: every case on that cell now runs under core validation. Run 536's ubuntu-glfw log shows llvmpipe (LLVM 20.1.2) and `effective pipeline: Gpu`, so `gpu_sync_validation` runs the path tracer, with `UPDATE_AFTER_BIND`/`PARTIALLY_BOUND` bindless available. That also makes `gpu_render_static`'s "no hosted runner exposes ray tracing" stale for the lavapipe cells: a coverage opportunity, out of scope here.
* Hazards fixed by reading: `VulkanBuffer::CopyToBuffer` (hence `RHIBuffer::Upload`) now waits for the destination's usage accesses before the copy (WAR/WAW); `RHIBuffer::PartialUpdate` does the same before its dispatch; `VulkanBLAS::Build` puts a build→build barrier before the build so a rebuild's reused scratch waits for the previous build submit. Not fixed: the TLAS instance buffer is still one host-coherent buffer rewritten while earlier frames' builds may read it (host writes are invisible to sync validation; the fix needs per-frame instance storage with full rewrites); the Metal argument buffer in-place patch (same class).
* Acquire semaphores (android `surface_loss_recovery`, VUID-vkAcquireNextImageKHR-semaphore-01779): `VulkanContext::BeginFrame` advanced `next_acquire_semaphore_index_` on every acquire attempt, so repeated failed acquires (`VK_ERROR_SURFACE_LOST_KHR`, `OUT_OF_DATE`) while the surface was gone cycled the ring onto a semaphore an in-flight frame still waited on. It advances only on `VK_SUCCESS`/`VK_SUBOPTIMAL_KHR` now; a failed acquire performs no signal operation (the layer records the signal only on success), so its semaphore is reused as is.

## Learnings

* When a change breaks an existing capability on some device, make the change work there, or fall back to the old behavior in that specific case. Never drop an existing feature from the support matrix to accommodate a new one: maximize feature coverage.
* CI toolchains are unpinned (`aminya/setup-cpp` installs the latest LLVM). clang-cl maps `-Wall` to `-Weverything`, so each new LLVM release can add warnings that fail only the Windows builds; `-Wpadded` and `-Wnrvo` are opted out in `CMakeLists.txt` for that reason.
* Android emulator (llvmpipe over gfxstream) screenshots are deterministic across CI runs of the same commit: two runs of step 0.2 gave identical FLIP (forward 0.0264, deferred 0.0404). A FLIP change on that cell is a real behavior change, not noise; `primitive_move` is the exception and varies between runs (0.018–0.026).
* CI runners are shared: cancel a run as soon as it has a failure that settles the question, and cancel runs superseded by a newer push (`mcp__github__actions_run_trigger` `cancel_workflow_run`). Push notes-only commits with `[skip ci]`.
* The android emulator (gfxstream over host lavapipe) advertises ASTC LDR and emulates it by decoding on the GPU when it intercepts a sync1 `vkCmdPipelineBarrier`; its `vkCmdPipelineBarrier2` skips the decode (fixed in gfxstream 9068c3aa). On that device only (`VulkanContext::CompressedImageBarriersNeedSync1`: android + llvmpipe), `VulkanCommandContext::Barrier` records image barriers on compressed-format images with sync1; every other barrier, and every barrier on other devices, uses sync2. Without it the ASTC material textures stay undecoded and the glTF models render almost black.
* First sync-validation CI run (ubuntu-glfw lavapipe): forward and deferred run clean under synchronization validation, and `sync_validation_hazard` confirms the gate reports a real hazard. `gpu_sync_validation` exposed the path tracer sampling its scene texture in `GENERAL` on frames without a dispatch (VUID-vkCmdDraw-None-09600), fixed in `GPURenderer::Render`. Three `VkSampler`s leak at `vkDestroyDevice` (reported after the verdict, so no case fails on it); the leak is still open.
